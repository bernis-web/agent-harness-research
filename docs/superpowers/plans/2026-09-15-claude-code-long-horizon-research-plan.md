> 面向执行智能体：如已安装 superpowers:executing-plans，按该技能逐任务执行；否则按本文阶段与验收门执行。默认单执行者，不自动启动并行代理。

## 1. 选题重新定位：研究问题来自哪里

### 1.1 对导师会议的理解

过滤闲聊和不确定的语音转写后，直接相关的内容是：

1. 导师关心从“聊天回答”到“完成实际软件任务”的能力变化及其底层组织方式。
2. 导师展示了用自然语言反复修改思维导图应用的过程，包括功能增加、交互修改、问题反馈和部署。
3. 使用者不只是给出一次提示，而是在过程中充当产品经理与测试者。
4. 导师建议先讨论、形成计划，再执行较大的项目。
5. 本研究应解释能力如何被组织出来，而不只是再做一个演示应用。

会议中“约二三十轮、不到五十轮”等说法是回忆性描述，不能直接作为实验样本量、耗时或成功率。转写没有提供完整开发日志，因而不能据此判断哪些具体机制已经发挥了作用。

这里将 cloude / cloud code 理解为 **Claude Code 编程智能体产品**，不等同于 Claude 基础模型、聊天网页或整个 Anthropic 产品家族。

### 1.2 推荐正式题目

**长程软件开发任务中智能体持续执行机制研究——以 Claude Code 为观察对象、以开源 Harness 为实验载体**

可用于向导师口头解释的一句话：

> 我想研究的不是它某一次代码写得好不好，而是它为什么能在反复修改需求、运行测试、出现错误甚至中断之后，仍然接着把一个软件项目做下去；再用可控实验检验支撑这种能力的机制。

### 1.3 不预设“效果很好”的结论

把“很好”拆成可测量的问题：

- 最终软件是否满足预先定义的需求？
- 新需求加入后，旧功能是否退化？
- 早期约束和后来修改过的约束是否仍被正确遵守？
- 中断后是否重复劳动、遗漏步骤或破坏已完成部分？
- 出错后能否利用反馈定位并修复问题？
- 为此用了多少调用、token、时间和人工干预？

项目需要允许出现“没有显著优势”“只在部分任务有效”“改进质量但增加成本”这些结果。

## 3. 三种开展方式与建议

| 方案 | 优点 | 局限 | 本项目定位 |
|---|---|---|---|
| 只做 Claude Code 行为观察 | 最贴近导师演示 | 很难独立控制其内部机制，不能可靠归因 | 必要的第一层 |
| 观察 + 官方/源码证据 + 可控消融 | 兼顾真实现象和机制检验 | 需要建设小型实验框架 | **推荐主方案** |
| 从零复刻完整产品 | 工程经验多 | 工期大、难控制变量、容易偏离科研问题 | 不采用 |

明确的结论边界：开源框架中的受控实验只能证明“该机制在此实验系统与任务集下的作用”，不能直接证明“Claude Code 内部就是这样实现的”。

## 4. 核心研究问题与假设

### RQ1：持续执行表现为哪些可观察行为？

在分阶段任务中，观察规划、读文件、修改、运行测试、接收反馈、再次修改、写进度记录、压缩或恢复等事件如何发生。允许记录公开可见的计划文本；不索取或猜测模型的隐藏思维链。

### RQ2：显式任务状态交接是否有助于跨阶段恢复？

候选假设：在相同模型、工具与重启节点下，结构化的任务状态记录，可能改善已变更需求的保持、恢复效率与回归控制。

这里的记录包含：当前目标、已生效需求、已撤销需求、已完成事项及证据、待办、失败状态、下一步。它不是保存聊天全文，也不是让人工替智能体填入答案。

### RQ3：可执行验证反馈是否有助于可靠修复？

候选假设：提供开发阶段测试的真实反馈，可能提升修复成功率和最终质量，但也可能增加调用与时间。

最终评分必须来自独立的隐藏测试，不能用智能体自行挑选的测试作为唯一成绩。

### RQ4：状态交接与验证反馈是否相互影响？

检查两者联合使用是否比单独使用更有益；样本较小时只报告探索性交互与不确定性，不强求显著结果。

### 可选 RQ5：不同压缩策略如何影响同一个任务的延续？

只在主流程稳定后，比较原计划中的 S1 近期截断、S2 自由摘要、S3 结构化摘要、S4 外置与受限检索。该实验是机制细化，不再代表整个选题。

## 5. 证据体系：避免把猜测写成源码事实

每条机制主张分四类登记：

- E1：官方公开说明，记录原文出处、访问日期与适用产品/版本。
- E2：固定提交的开源源码事实，记录文件、行号或符号、必要的测试证据。
- E3：本次研究直接观察到的行为，关联 run_id 与 event_id。
- E4：解释或假设，明确其依据，以及需要什么实验才能检验。

证据矩阵字段：claim_id、claim、evidence_type、source、version、observed_event、supports、does_not_support、verification_status。

例如，观察到智能体在新会话先读取进度文件，能支持“它在该次运行读取了进度文件”；不能单独支持“它不读这个文件就一定失败”。

## 6. 实验 A：Claude Code 行为观察

### 6.1 观察对象与可比性

首轮选择 2 个受控案例；之后扩展到 6 个，每个正式观察案例先运行 1 次。它们用于过程解释与失败分类，不用于宣称产品排行榜。

记录客户端版本、模型标识、运行日期、可公开的工具清单、权限条件、操作系统、初始仓库提交、研究者提供的指令，以及是否启用自定义记忆、技能或插件。不得通过读取用户全局配置来获得这些信息；采用专用、经用户确认的实验配置。

原始观察使用预先冻结的默认/标准配置。若后续加入本研究设计的状态文件，必须命名为“研究者增强条件”，不能再称为原生默认行为。

### 6.2 任务采用六阶段，而不是一次性提示

每个案例至少包含：

1. 阅读初始需求与初始仓库，提出可见的执行安排。
2. 完成最小可用功能。
3. 接收一次明确的需求变更。
4. 修复一个预先定义的问题，同时保持旧功能。
5. 接收第二次增量需求或授权后的会话恢复任务。
6. 自查、提交最终产物并接受独立评分。

阶段用户消息必须提前写好，所有观察使用同一份脚本。默认不允许研究者根据某组表现临时提示答案。额外人工帮助单独记录，并将该运行标为人工干预条件。

Claude Code 的自然上下文压缩只在实际出现且可从授权日志确认时登记。若未出现，不得说“已经测过压缩”。主动新开会话属于外部施加的恢复测试，不能称为其自然自动压缩。

### 6.3 事件记录

记录可观察的消息、工具类别、动作对象、结果状态、测试运行与失败摘要、代码差异、阶段开始/结束、可确认的压缩/恢复事件及用量来源。收集范围仅限本项目新产生且经授权的日志。

每个关键解释至少链接一个事件和一份相应代码/测试产物。没有公开 token 或成本数据时记为 null 并说明原因，不能记为 0 或拿字符数冒充实际 token。

### 6.4 输出与验收

输出 2 个先导案例的事件时间线、阶段状态图、需求保持表与失败案例分析。验收不要求任务成功，但要求可追溯、无泄漏、评分独立且失败不被删除。

## 7. 实验 B：固定模型下的 2×2 机制消融（主实验）

### 7.1 为什么不直接在 Claude Code 里消融

不能假定用户界面中的开关能完全关闭 Claude Code 内部的规划、记忆或验证。主消融在可控的小型 Harness 中实现；Claude Code 作为观察对象单列，不强行与不同模型、不同权限的运行混在一起排名。

### 7.2 四个条件

| 条件 | 结构化跨阶段状态 | 开发阶段测试反馈 |
|---|---|---|
| C00 | 无 | 不返回真实测试反馈 |
| C10 | 有 | 不返回真实测试反馈 |
| C01 | 无 | 返回真实测试反馈 |
| C11 | 有 | 返回真实测试反馈 |

固定同一模型标识、采样参数、初始任务、阶段消息、工具接口、资源上限与重启节点。这个设计检验的是“状态交接”和“可用验证反馈”，不是全部 Harness 与无 Harness 的总差异。

“无状态”不是无代码或无文件系统：四组均保留工作代码；区别只是实验指定的跨会话状态通道是否存在。代码本身也能承载信息，这属于设计边界，须报告。

### 7.3 状态通道的精确定义

- 在第 2、4 阶段完成后，四组执行同样的干净会话重启，清空消息历史。
- 重启输入均包含相同初始任务说明、当前阶段的新指令、工具说明及当前工作代码的访问权；不自动重新提供之前全部变更消息。
- C10/C11 可在阶段结束前由智能体维护研究规定的状态文件，重启时读取它；总状态上限为 2,000 个模型 token，具体计数器在预实验冻结。
- 状态字段：goal、active_requirements、superseded_requirements、completed_with_evidence、pending、known_failures、next_action。
- C00/C01 不挂载该状态文件，不把聊天、计划或交接摘要从旁路恢复。工具读写限定到任务声明的文件，禁止另写研究指定以外的交接文件。
- 不为了彻底消除所有潜在记忆而删代码或代码注释。检查是否存在明显旁路交接行为，报告并做敏感性分析，而不是静默删掉不利样本。
- 不能把被摘要的原始历史、隐藏测试、评分答案或研究者人工整理的正确状态注入“有状态”组。
- 若 token 计数器不能可靠取得，暂停正式预算匹配；字符估计仅用于离线开发，并清楚标记。

### 7.4 测试反馈通道的精确定义

四组均通过相同受限接口读取/修改工作代码，不提供不受控的通用 shell、网络或隐藏评分目录访问。

- run_public_tests 在 C01/C11 中运行公开开发测试，返回真实但长度受限的退出状态、错误与诊断。
- C00/C10 调用相同接口时只收到固定的“本条件不提供测试反馈”响应，不返回结果或暗示通过。
- 隐藏测试由独立评估器在阶段结束后运行；分数不得回传给智能体用于迭代。
- 公开测试输出中的文本也按数据处理，不把它提升为运行器指令。
- 禁止通过其他工具绕过反馈控制；若运行环境不能隔离这些通道，不能称该消融有效。
- 条件名称只描述外部验证反馈；模型仍可自行检查代码，不声称关闭了它的所有自我检查能力。

### 7.5 样本与运行矩阵

- 离线开发：2 个独立先导任务，不进入正式统计。
- 首次真实先导：2 任务 × 4 条件 × 1 重复 = 8 次可控运行；另做 2 次 Claude Code 观察，共 10 次。
- 正式最低建议：12 个正式任务 × 4 条件 × 2 重复 = 96 次可控运行；另做 6 个 Claude Code 观察案例，共 102 次。只有用户另行批准才启动正式批次。
- 12 个正式任务分属 3 个任务族，每族 4 个真正不同的任务规格，不用换变量名凑样本。
- 若预算足够，扩为原计划的 20 任务 × 4 条件 × 2 重复 = 160 次可控运行。新增观察和压缩子实验不包含在该数目内。
- 2 次重复主要记录随机波动，不能把重复当作新的独立任务。任务族相似性也必须纳入解释。
- 采用按任务分块、随机化条件顺序的运行计划，记录调度种子；服务商不保证 seed 时如实写明。

### 7.6 任务族

**A. 数据处理小工具：** CSV/JSON 输入、字段验证、聚合、导出、接口兼容与错误处理。用固定本地数据，禁止访问私人文件。

**B. 工作流/服务逻辑：** 本地任务清单、状态转换、持久化和导入导出。无需公网部署、真实账户或生产数据库。

**C. 思维导图核心逻辑：** 作为导师演示的缩小、可评分版本，处理节点、父子关系、变更、合并、折叠状态和导入导出。主实验用结构化输入和确定性测试，不把自动理解任意自然语言或美观度混入主要评分。

推荐先导案例为一个数据处理任务和一个思维导图逻辑任务。GUI 演示可后做，不作为第一阶段阻塞项。

## 8. 指标、评分和统计

### 8.1 主指标

1. **端到端任务成功：** 最终全部关键隐藏测试通过，且没有规定的禁止行为。只要关键项失败就不是成功；另报连续分数以保留部分完成信息。
2. **有效需求遵守率：** 每一阶段满足的当前有效需求数 / 当前有效需求总数。明确排除已经撤销的要求。
3. **回归破坏率：** 本阶段失败、但前一阶段通过且仍适用的检查数 / 前一阶段通过且仍适用的检查数。分母为 0 时记 null。

### 8.2 次指标

- 恢复到第一个有效进展所需调用数与时间；未恢复时登记超限/失败，不填 0。
- 预置缺陷修复率及修复后旧功能保持情况。
- 每阶段和每次运行的输入、输出、缓存、摘要等实际用量及来源。
- 总耗时、工具调用数、重试次数、人工干预次数。
- 状态文件中遗漏、过期、错误和缺少证据的条目数。

“有效进展”在任务评分表中事先定义为至少一个阶段目标首次通过且未破坏关键旧目标；不能事后挑选对某条件有利的标准。

### 8.3 评分防作弊

- 公开开发测试和隐藏评分分开存储；后者不挂载给智能体，也不出现在检索索引中。
- 优先采用行为测试；命名、禁止依赖等可用 AST/规则补充，不能只用正则搜索“看起来像对的代码”。
- 先用人工构造的正确、错误和边界样例验证评分器，而不是依赖实验模型给自己打分。
- 生成代码的运行必须在经确认的隔离环境中，限制网络、路径、运行时间和资源；普通子进程不是完整安全沙箱。
- 隔离能力未就绪时，只做静态/合成评分自测，不执行未知模型生成代码，不宣称完成端到端评测。
- 禁止人工观察成绩后再修改隐藏测试来偏向某组。确需修正评分错误时，版本化并对全部受影响条件重评。

### 8.4 分析方法

以同一任务为配对单位，报告各条件的原始成功数、均值/中位数、差异和不确定区间。对二元成功结果与连续遵守率分别分析；相关重复保留在同一任务块中。小样本及任务族相似性作为局限明确写出。

C11−C01 和 C10−C00 描述状态通道在两种反馈条件下的差异；C11−C10 和 C01−C00 描述反馈通道的差异。交互作为探索性结果，分析脚本必须保留逐任务结果，不只输出柱状图。

预算/时间超限计入该条件的端到端未成功，同时单列原因。网络或服务故障按预先冻结的重试规则处理，并同时报告计划运行数、有效运行数和故障数；不只报告幸存运行。

零差异和负结果仍应提交完整数据与失败解释，不能承诺一定得到“显著提升”。

## 11. 预算、停止规则与运行安全

以下是建议的先导资源边界，不构成付费授权；模型能力和任务长度不匹配时，在正式冻结前调整并记录。

- 付费调用默认关闭；先导总授权范围最多 10 次运行。
- 每次运行建议最多 60 次模型请求、120 次工具调用、30 分钟；工具执行单次超时另设并预先冻结。
- 每次运行建议累计输入与输出 token 总上限 120,000，包含摘要、状态生成和重试；若客户端无法可靠测得用量，先解决计量或明确采用可执行的费用硬上限，不声称 token 上限已生效。
- 本币预算上限必须由用户给出；没有批准的数额，不启动付费调用，也不根据旧代理或账户配置猜测。
- 超时或服务错误每个调用最多重试 2 次，重试计入所有预算；达到次数后记录失败并停止该运行。
- 请求前预留最大输出预算，不能仅在扣费之后检查上限。价格信息按实际批准端点与运行日期核对，不把第三方转发价当作官方价。
- 实验沙箱不含主机凭据、私人资料和隐藏评估文件；不挂载整个用户主目录，不关闭审批来追求无人值守。
- 接口不可用时报告并保留状态，不擅自切换模型、端点或供应商，否则破坏控制条件。

用户只需确认：允许的产品/API 与模型、先导费用上限、可用于运行生成代码的隔离方式。以上未确认时，P0/P1 仍可离线推进。
