# 计划 07:KV-cache 友好的上下文管理(最"底层"的方向)

> 定位:定量实验(系统层) | 难度 ★★★ | 周期 3-4 周 | 产出:缓存命中率实验 + harness 缓存友好设计清单
> 对应课程子方向:上下文管理、工具管理

## 一、研究意义

推理成本与首 token 时延的大头在 prefill;KV-cache 命中可以把这段开销降到原来的十分之一以下。harness 的每一个设计决策——系统提示放哪、工具 schema 何时注入、历史消息是否重排、compaction 何时触发、子代理共享多少前缀——**都在决定缓存命中率**。Manus 公开的经验("保持前缀稳定")证明这是实战中的重要杠杆,但:

1. 公开的系统对比数据几乎没有(各框架默认配置的缓存效率未知);
2. compaction/工具清理等"上下文卫生"策略与缓存命中存在**内在冲突**(重开窗口=缓存全失效),这个冲突没有被定量刻画过;
3. DeepSeek API 的响应直接返回 `prompt_cache_hit_tokens` 等字段,提供了最干净的测量口径——研究对象(dsh/DeepSeek 生态)与实验条件天然契合。

这是六个子方向里最贴近系统底层的一个,结论可直接变成"harness 设计清单",工程价值最即时。

## 二、研究现状及实验室研究基础

- **工程经验**:Manus 博客提出稳定前缀、结构化提示以最大化命中;Anthropic/LangChain 的上下文工程文章聚焦信息质量,未覆盖缓存维度。
- **测量条件**:DeepSeek API 明确返回缓存命中 token 数与差异计价;OpenAI 兼容生态亦有自动前缀缓存——实验可程序化记录,无需黑盒估计。
- **空白**:①"上下文卫生 vs 缓存命中"的权衡曲线;②harness 典型操作(注入检索结果/插入系统提醒/压缩/工具结果清理)对命中的冲击量化;③各框架默认配置的缓存效率横评。
- **实验室基础**:Python + DeepSeek API(成本极低,缓存命中本身省钱)+ 任意开源 harness/自建 loop;无 GPU 需求。

## 三、研究内容及研究计划

### 3.1 研究内容

1. **基线测量**:同一多轮任务下,四种消息组装方式的命中率曲线——
   - A1 严格追加(前缀永不改动);
   - A2 每轮在系统提示后插入"动态日期/环境"块(常见做法);
   - A3 每轮注入检索结果到历史中部;
   - A4 compaction 触发后重开窗口。
2. **破坏半径实验**:在长会话第 k 轮执行单次"历史编辑"(模拟工具结果清理),测量命中断点之后所有轮次的累计额外成本——得到"一次清理值多少 token"的换算。
3. **工具注入策略**:工具 schema 全量常驻 vs 首轮后移出(旧工具不再出现)vs 动态挂载,对命中率与任务成功率的双影响(与计划 02 联动)。
4. **指标**:`prompt_cache_hit_tokens` 命中率、输入成本(命中/未命中差异计价)、首 token 时延、任务成功率(验证缓存策略不伤质量)。
5. **产出设计清单**:前缀分层(绝对稳定→缓慢变化→每轮变化)、清理操作的时机建议、compaction 触发点与缓存损失的联合优化。

### 3.2 周计划(4 周)

- W1:测量脚手架(记录每轮请求的缓存字段)+ A1-A4 实现。
- W2:基线与破坏半径实验。
- W3:工具注入实验;成功率对照(确认缓存策略无质量代价)。
- W4:汇总清单与报告;可选:测 dsh/deepagents 默认配置的命中率横评。

### 3.3 预期产出与验收标准

- 产出:测量工具、四组实验数据、权衡曲线、"一次清理/一次压缩的成本换算表"、设计清单。
- 验收:每种组装方式 ≥20 轮会话 × 3 重复;清单每条建议都对应一条实验证据。

### 3.4 风险与退路

- 风险:服务端缓存策略不透明(命中阈值、保留时长)→ 用控制变量与多次重复缓解;报告注明测量日期与端点版本。
- 风险:与计划 02/01 并行时工作量超载 → 本计划可独立成篇,也可作为 01/02 的附加观测维度合并执行。
