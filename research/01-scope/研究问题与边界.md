# 研究问题与边界(P0 交付)

> 版本:2026-09-15 | 状态:待用户审核 | 上游依据:docs/superpowers/plans/2026-09-15-claude-code-long-horizon-research-plan.md §1、§4

## 1. 导师真正的问题(从会议转写过滤后)

导师展示的不是"一次提示生成一个应用",而是:**用自然语言在几十轮里持续迭代一个真实软件**(功能增加、交互修改、缺陷反馈、部署)——用户在其中充当产品经理与测试者。他关心的是这种"从聊天回答到完成软件任务"的能力变化**是如何被组织出来的**,并建议先讨论、形成计划,再执行大项目。

转写中"约二三十轮"等数字是回忆性描述,不作为样本量或成功率依据;转写无完整开发日志,不据此判断具体机制是否起过作用。

## 2. 正式题目与日常语言解释

**长程软件开发任务中智能体持续执行机制研究——以 Claude Code 为观察对象、以开源 Harness 为实验载体**

一句话版:我想研究的不是某次代码写得好不好,而是这类智能体**为什么能在反复修改需求、运行测试、出错甚至中断之后,接着把一个软件项目做下去**;再用可控实验检验支撑这种能力的机制。

## 3. 研究问题与证据方式

| RQ | 问题 | 主要证据方式 | 对应实验 |
|---|---|---|---|
| RQ1 | 持续执行在分阶段开发中表现为哪些**可观察行为**(规划、读改文件、跑测试、接收反馈、写进度、恢复)? | E3 行为观察 + E1/E2 机制解释 | 实验 A(Claude Code 观察,2→6 案例) |
| RQ2 | **结构化跨阶段状态交接**是否改善需求保持、恢复效率与回归控制? | E4 假设 → 实验 B 因果检验 | 实验 B 状态通道(C10−C00, C11−C01) |
| RQ3 | **开发阶段测试反馈**是否提升修复成功率与最终质量、代价是什么? | E4 假设 → 实验 B 因果检验 | 实验 B 反馈通道(C01−C00, C11−C10) |
| RQ4 | 状态交接与测试反馈是否**交互**(联合使用是否优于单独)? | 探索性分析(小样本不强求显著) | 实验 B 交互项 |
| RQ5(可选) | 不同压缩策略(S1—S4)如何影响同一任务的延续? | 固定历史延续实验 | 实验 C(主流程稳定后单独批准) |

结论边界:可控系统中的消融只证明"该机制在此实验系统与任务集下的作用",**不**证明 Claude Code 内部就是这样实现的。

## 4. 明确不做

- 不从零复刻完整 Claude Code;不训练/微调模型。
- 不在 Claude Code 内部做机制消融(无法确信关闭其内部规划/记忆/验证)。
- 多智能体编排、缓存成本实验(拓展计划 07)、完整 GUI 演示:暂不进入主实验。
- 不读取凭据、全局聊天记录、.zcode 配置;不把会议闲聊原文放入公开仓库。
- 不预设"效果很好":允许"无显著优势/仅部分有效/提质增耗"结果。
