## B2(高)续跑"执行状态未知"

- **问题**:"intent 后 applied 前崩溃→按 intent 重放"把"无完成日志"误判为"未执行";该窗口内副作用可能已完成。
- **统一规则(唯一)**:intent 存在而无 applied = **执行状态未知**;按 operation_id 核对 `.result` 文件+内容哈希+已提交评分记录+完成标记后再分类。持久化顺序(文件协议):结果写盘 fsync → 完成标记 `ops/<op>.done`(含哈希)fsync → 事件追加。逐类别幂等依据表(套件更新=固定脚本原子替换;快照=不可变;探针/评分=一次性工作目录可重复;API 请求=不可重放→pending_verification 不自动重发)。HARNESS_FAULT 故障点扩为 before_effect / after_effect_before_applied / after_applied_before_checkpoint / score_persisted_before_log。

## B3(高)判定协议统一

- **问题**:修复成功两处定义不一致("S4 末与终评" vs "S4 末/终评",且缺回归条件);缺每阶段隐藏评分时点;回归分母与恢复进展不可计算。
- **统一规则(唯一)**:
  1. **repair_success ⟺ S3 基线确认缺陷存在 ∧ S4 末探针通过 ∧ S6 末探针仍通过 ∧ S4/S6 评分点未破坏此前通过且仍适用检查**;S6 才通过=late_repair(单列,不计 S4 持续修复成功)。三文件同一定义。
  2. **S1–S6 每阶段末**对冻结代码快照执行当前有效检查生成 Score(S3 缺陷基线为额外前置观测);评分后状态窗口仅 STATE.md 可写、任务代码写拒绝,窗口调用计入预算——被评版本=带入下阶段版本。
  3. **回归集合**:D_s=上一阶段已通过∧当前仍适用∧语义未变的 check_id 集合(撤销/改义经版本化映射排除);N_s=D_s 中当前失败;denominator=|D_s|、count=|N_s|、ratio=null(当 |D_s|=0)。**恢复进展相对重启前最后阶段快照**:基线已通过再通过不算进展;新增生效需求首次通过或先前失败且仍有效检查转通过为候选,再验持续关键项;S3 基线不计未生效的 S4 要求。
- **位置**:评分规则.md:20–28(§2 指标 3 集合定义)、:49–54(§3 边界表增 JSON 数值比较行)、:57–65(§4 统一修复判定/每阶段评分/恢复基线)、:74(正确实现样例分母=|D_s|)、:79(九类自测场景);运行器设计.md:28–37(§3.1 每阶段 score_recorded/状态窗口限制)、:82(修复率统一判定)、:111(V-B3);数据契约.md:98(Score.repair_status 枚举)、:69–75(事件不变式含 score_recorded/state_write)。
